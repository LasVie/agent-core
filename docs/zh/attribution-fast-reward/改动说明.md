### 3.2 提交二：Fast Reward + 保留过程信号（问题 3、4、5、7）

**新增 `openjiuwen/agent_evolving/fast_reward/`（整个包，含 `metrics/`）**

- 即我们的 Fast Reward。它从用户请求写出判定标准：要求项是用户要的，挑战项是同类最好作品会做的。然后实际运行交付物取证，逐条判定，最后用代码计分。
- 评测知识文件 `metrics/game.md`、`metrics/picture_book.md`、`metrics/personal_assistant.md` 只写原则，不写具体数字或题目规则。按任务里的关键词自动选用：
  - 「帮我安排」「日程」「行程」等 → 个人助手；
  - 「游戏」「小游戏」等 → 游戏。
- 页面类交付物需要 Playwright。同事环境的 `.venv` 里已有 `playwright` 包；浏览器内核用 Playwright 默认缓存。
- 测试：新增 `tests/unit_tests/agent_evolving/fast_reward/`（3 个文件，67 个用例）。

**新增 `openjiuwen/agent_evolving/attribution/reward/fast_reward_adapter.py`（225 行）**

- `fast_reward_enabled()`：默认启用。设环境变量 `ATTRIBUTION_REWARD=agent` 则回到原来的 Reward deep agent。
- `route_from_model(model)`：从 JiuwenSwarm 传入的 core `Model` 读出 `model_name`、`api_base`、`api_key`、`client_provider`、`timeout`（有 `extra_body` 也带上），作为 Fast Reward 的模型路由。读不到（例如模型组）就报错，提示设 `FAST_REWARD_CONFIG`。
- `fast_reward_config(model)`：
  - 有 `$FAST_REWARD_CONFIG` 或 `~/.fast_reward/config.json` 时用它；
  - 否则出题、判定、取证都用诊断模型；
  - `deadline_seconds` 默认 600，可用环境变量 `FAST_REWARD_DEADLINE` 改。
- `existing_paths(paths)`：只给 Fast Reward 还存在的交付文件。
- `final_reply(task_parse, nodes)`：从消息产物里取**用户最后收到的那一条**，跳过成员在团队内部的消息，作为 Fast Reward 的回复文本。
- `to_reward_payload(result, language)`：把 Fast Reward 结果转成原有的 `attribution.reward.v1` 格式，前端和归因看到的字段不变。
  - 每个判定项变成一个 dimension：`requirement` 前缀「[要求]」或「[挑战]」，`comment` 是判定理由。
  - **档位由判定结论决定，不看分数**（提交三）：

    | 判定项类型 | 满足 | 部分满足 | 不满足 |
    |---|---|---|---|
    | 要求项 | perfect（跳过归因） | fair | weak |
    | 挑战项 | perfect（跳过归因） | fair | fair |

  - 每个 dimension 多带一个 `tier` 字段；`run_diagnosis` 用它覆盖原来按分数段（≥90 perfect、75–90 fair）推出的档位。所以只要判定项没满足，就一定进入归因，与分数无关。
  - `score` 字段只用于展示，取 Fast Reward 自己的判定项分数（满足 100、部分 50、不满足 0）。
  - 挑战项没做到只算 fair（有改进空间，不算缺陷）。
  - 证据不足无法判定（unknown）的项不生成 dimension，只在总评里写「另有 N 项因证据不足未能判定」。
  - 总分没有（无证据）或一条都没判定出来时，报错，按 Reward 失败处理。
- `run_fast_reward(...)`：
  - 输入：任务用 `task_parse.user_request`（用户原话，没有时退回 `task_description`）、存在的文件产物、最后一条回复、用户补充信息；
  - 运行过程中逐步向状态接收器发 `stage="reward"` 事件（见 3.4）；
  - 返回 payload 和 `run_meta["reward"]`（engine、artifacts、claims 数、warnings 等）。

### 3.3 提交四：「何时何地做」类判定项按用途判（泳镜问题）

起因：单 Agent 个人助手那次，计划把泳镜放在游泳课后（11:00–11:30）买，可 10 点上课就要用。Fast Reward 却把「泳镜在哪买、何时买顺路」判成满足。原因是判定模型只看到判定项本身，看不到任务，不知道这个时间安排是为了什么。

**`openjiuwen/agent_evolving/fast_reward/pipeline.py`**（`evaluate_terminal`，约第 83 行）
- 给判定模型的输入新增 `"task"`（任务原文）。

**`openjiuwen/agent_evolving/fast_reward/prompts.py`**（`JUDGE_PROMPT`，加 3 行原则）
- 判定时要结合任务看：关于在哪、何时、怎么做的判定项，只有这个安排也满足任务对它的用途才算满足。例如结果需要之后才去办的事，不算「顺路」或「及时」，路线再方便也不算。

**`openjiuwen/agent_evolving/fast_reward/metrics/personal_assistant.md`**（原则级，不针对具体题目）
- 第 2 条「可行」补充：每一步需要的东西（要买或带的物品、证件、人）要在那一步之前到位；需要它的时刻之后才「顺路」去办，不算服务了它的用途。
- 「怎么判」新增「把每个需要追到它被用的那一步」：用户隐含的依赖也算（坏了要换的东西，下次用时就需要），检查它是否先到位。

**`tests/unit_tests/agent_evolving/fast_reward/test_fast_reward.py`**：加一处断言，判定模型的输入里有任务原文。

这些改动也同步到了我们自己的 `agent-core-reward-delivery`，两边的 Fast Reward 保持一致。

**验证方式：** 这边连不到模型。`attr-fix-handoff/demo/check_goggles.sh` 会用这个分支的 Fast Reward 重新评那次的 `schedule.md` 和回复，最后列出所有涉及泳镜的判定项。前端里重跑那个会话的诊断也可以验证。

### 3.4 提交五：诊断进度逐步显示；信号按「先看问题」排序（第 8 项里 agent-core 能做的部分）

> 新版 JiuwenSwarm（`289e09330`）把以 `llm-数字 · ` 开头的行折叠进「N 次模型请求」，进度行默认看不到；按 JiuwenSwarm 的设计为准，见 3.10。

**`openjiuwen/agent_evolving/attribution/reward/fast_reward_adapter.py`**
- 新增 `_ProgressLines`：作为 Fast Reward 这次运行的进度对象（Fast Reward 自带按运行隔离的进度槽，结束后恢复原值），同时接收 Fast Reward 的日志。每走一步就发一条 `stage="reward"` 状态事件，`response_preview` 是一行进度，形如：
  `▓▓▓▓▓░░░░░ 48% · 取证：第 3 项检查完成（browser） · 已用 1分52秒`
- 显示的步骤：
  - 出题开始；
  - 出题完成（N 个维度）；
  - 取证开始；
  - 每完成一项检查；
  - 取证结束；
  - 判定开始；
  - 每判定完一个维度；
  - 完成（总分）。
- 进度只增不减，各阶段占比：出题约 0–12%，取证 15–68%（按检查数推进），判定 70–98%，完成 100%。
- JiuwenSwarm 原样把每条事件渲染成「诊断分析」下的一行（前缀 `llm-N · reward · 成功 · 模型名` 是 JiuwenSwarm 的固定格式），所以会一行行地刷出来。
- `to_reward_payload`：维度按「没满足的要求 → 部分满足的要求 → 没做到的挑战 → 已满足」排序；总评开头加一句计数，如「要求 14/15 满足 · 挑战 3/6 未做到。」。

3. 一份交付物都没框到 → 不跑 Fast Reward，不出产物改进，只看过程信号。

### 3.9 提交十（`b51ff5d9`）：按 leader 的「最后交付的那一轮」决定评不评交付物；当前有效的需求清单

起因：提交八、九之后，「交付物是不是最终版」要靠模型逐条判断回复和文件有没有被取代，摘要里为此加了好几段。qwen 两次判错，代码也越来越绕。和你讨论后改成一条规则：

**规则**
1. **最后交付的那一轮**：用户本人的每条消息开始一轮，到下一条为止。按规则取「最后一个写过或发出过文件的轮次」；没有这样的轮次，就取最后一个回复有一定长度（合计 ≥ 50 字）的轮次，这样结尾的「谢谢 / 不客气」会被跳过。
2. **模型只在一种情况下起作用**：任务解析的模型会指出「最后一次交付是从哪条用户消息开始的」（`report_delivery_round`）。只有在规则选出的轮次没有发过文件（纯回复）时，才改用模型指出的、确实有交付的那一轮。例如交付之后用户又问了个顺带的问题、agent 长篇回答，这时以模型为准。只要有文件发出，就以文件为准。
3. **评不评交付物**：框选里有 leader（单 Agent 时是主 Agent）**在这一轮里干活的节点**（用户自己的那条消息不算），才评交付物；只框了成员，或者 leader 只框到别的轮次，就不评交付物、不跑 Fast Reward、不出产物改进，只看过程信号（失败的工具调用和判为反馈的用户追加消息）。
4. **评哪些**：这一轮 leader 的最后一条回复；任务解析报的文件里，在这一轮最后写过或发给用户的那些。早几轮的版本（比如改名前的 `schedule.md`）不评。
5. **当前有效的需求清单**（`report_requirements`）：把用户所有消息里对结果的要求合并成一份。后面的修改以后面为准，被推翻的旧要求不写；确认、回答、闲聊和只关于做法的话（「用 agent team 做」）不写；用户纠正或抱怨过的点标 `corrected`。
6. **交给 Fast Reward 的任务**依次是：
   - 「用户补充（最高优先级；与下面冲突时以此为准）」：诊断时填的补充说明；
   - 「当前有效的需求清单」：用户纠正过的排前，每一条都要有对应的要求项；
   - 「用户原话」：用来核对细节，与清单不一致时以清单为准。

   补充说明仍照旧传给 Fast Reward，转成判定项；这些项在诊断分析里标「（用户补充）」，同一档里排最前。

**删掉的**（提交八、九加的）：摘要里的「整个会话里给用户的回复」「整个会话里写过的文件」「框选之外的后续进展」；`report_final_reply`、`report_final_files` 两个工具；回复和文件的兜底规则；「本次评估范围」说明；`TaskParseResult.deliverables_outside_selection`、`selection_partial`。

## 6. 需要和同事确认的点

1. **模型组**：如果诊断模型是「模型组」，`route_from_model` 可能读不到单一的 endpoint，会退回规则信号并提示设 `FAST_REWARD_CONFIG`。需要的话再支持取组内第一条路由。
2. **规则信号**：提交八起规则只取失败的工具调用和用户追加的消息；提交九起，用户追加的消息再由任务解析的模型判断是不是反馈，只有反馈进归因。模型判错时，真正的不满可能被漏掉。
3. **挑战项的档位**：挑战项没做到给 fair，会进入归因。如果你们觉得 Demo 里不该有这类「锦上添花」的建议，把 `_CHALLENGE_TIER` 里的 `partial`、`unmet` 改成 `perfect` 即可（一处）。
4. **Skill 建议**：`submit_skill_improvement` 在归因提示词里仍是可选的。是否给出 Skill 建议，取决于归因 agent 是否判断问题源于 Skill 或派发方式。本次没有改归因提示词。
5. **耗时**：Fast Reward 默认最多 600 秒，网页类交付物取证较慢；要压时间可设 `FAST_REWARD_DEADLINE`。
6. **最后交付的那一轮**（提交十）：主要靠规则判断（写过或发出过文件的最后一轮），模型只在纯回复的情况下起作用。如果最后一轮写了文件但不是交付（比如只写了测试脚本），这一轮会被当成交付轮，评的是任务解析报的文件和这一轮的最后回复。
7. **过程模式的诊断目前只有规则信号**：还没有「过程评审」（按效率、环境、Skill 用法逐项给判定）。过程中没有失败的工具调用、用户也没追加反馈时，结论就是「没有可归因的信号，无需归因」。
8. **只框成员不评交付物**（提交十）：哪怕框到的是成员在最后一轮写交付文件的那段，也只看过程。想评结果，要把 leader 在最后一轮的部分框进来。
